# 红蓝对抗平台 — 心得体会

---

## 一、从课堂到实践的跨越

在参与红蓝对抗平台项目之前，我对 AI Agent 安全的理解主要停留在理论层面——提示词注入、越权攻击、工具滥用这些概念在论文和课程中都见过，但从未亲手构建过一个完整的对抗系统。这次项目让我真正从"学习者"转变为"构建者"，从知道"是什么"到理解"怎么做"。

作为组长和架构师，我需要从零开始思考一个完整的系统应该是什么样子。需求的梳理、架构的设计、模块的划分、数据流的走向，每一个决策都需要深思熟虑。这个过程让我深刻体会到，软件工程不仅仅是写代码，更是在各种约束条件下做出最优选择。

## 二、架构设计中的权衡

在架构设计阶段，我面临的最大挑战是确定系统的编排方式。红蓝对抗是一个多阶段、有状态、可回溯的流程，如果使用传统的函数调用链或简单的 if-else 控制流，代码会变得难以维护。经过与组员讨论和查阅资料，我选择了 LangGraph 状态图编排方案。

三节点模型（攻击链规划 → 防御分发 → 评估流）看似简单，但它优雅地解决了状态传递和流程控制的问题。每个节点只关心自己的输入和输出，节点之间的路由由状态图自动处理。这个设计让我意识到，好的架构不是把问题复杂化，而是用合适的抽象把复杂问题简单化。

双总线架构的设计同样经过了反复权衡。一开始我考虑过使用单一事件总线，但很快发现执行路径和可观测路径的需求完全不同——一个要求同步、可靠、可预测，另一个要求异步、非阻塞、可扩展。将它们分离为 Fast Path 和 Slow Path，既保证了执行流程的确定性，又不影响可观测性功能的扩展。这个设计让我体会到，软件架构的核心在于"分离关注点"。

## 三、与老师交流的收获

在开发过程中，我多次与老师交流技术方案。其中让我印象最深的是关于蓝队检测策略的讨论。最初我设计的蓝队主要依赖关键词匹配，认为这是最直接有效的方式。老师指出，关键词匹配虽然简单，但很容易被同义词替换、语序变换等方式绕过，建议引入语义检测能力。

这个建议让我重新思考了蓝队的设计。最终我们采用了规则引擎和 LLM 模型双通道并发检测的方案——规则引擎负责快速、精确的关键词和模式匹配，LLM 模型负责语义层面的理解。两个通道的结果合并后，检测的准确率和覆盖率都有了明显提升。

另一个重要收获是老师建议引入 RedBench 基准数据集。之前我主要依赖 LLM 生成攻击提示词，但 LLM 生成的质量不稳定，有时模型会拒绝生成攻击内容。RedBench 数据集的引入解决了这个问题，它不仅提供了大量高质量的攻击样本，还提供了基线对比数据，让评估报告更有说服力。

## 四、攻克技术难关的过程

红队自动进化失败是开发中遇到的最棘手的问题。变异流程本身不复杂——检测到攻击被阻断后，调用 LLM 对 Payload 进行重写。但 LLM 的输出格式极不稳定，有时返回 JSON，有时返回纯文本，有时还带 Markdown 标记。最初的解析代码只处理了 JSON 格式，导致大量变异失败。

我和组员一起分析了几十次失败的 LLM 输出，发现主要有三种格式：标准 JSON、带字段名的字典、纯文本。根据这个发现，我设计了多层容错解析策略：先尝试 JSON 解析，失败后尝试从字典中提取常见字段，再失败就剥离 Markdown 标记取纯文本。三层容错覆盖了所有已知的 LLM 输出格式，变异成功率从不到 50% 提升到了接近 95%。

另一个难题是模型拒绝生成恶意攻击提示词。开源模型如 dolphin-mistral 内置了安全限制，当系统提示词中包含"生成攻击内容"之类的表述时，模型会直接拒绝。我们尝试了多种系统提示词，最终发现将任务定位为"安全评估测试"而非"攻击生成"，模型就愿意配合了。这个经验让我认识到，与 LLM 打交道需要"沟通技巧"，用合适的上下文引导模型产出期望的结果。

## 五、团队协作的体会

三人团队虽然规模不大，但分工明确、沟通高效。组员一负责红方核心功能，组员二负责蓝方核心功能，我负责架构设计、前端开发和整体协调。这种分工让每个人都能专注于自己的领域，同时通过接口契约保证协作顺畅。

让我印象深刻的是，在前端开发过程中，我遇到了一个数据展示的问题，需要红方接口返回额外字段。组员一当天就完成了接口调整，没有影响我的开发进度。同样，组员二的蓝队检测模块需要依赖事件总线，但事件总线在我负责的架构层，我们提前约定了接口契约，他按照契约开发，最后联调时几乎没有遇到问题。

这个经历让我认识到，团队协作的关键在于提前约定接口和分工、互相信任和及时沟通。这次项目中，每周中我们都会进行简短的进度同步，确保每个人的工作都在正确的轨道上。

## 六、技术成长的收获

通过这次项目，我在多个技术领域有了实质性的提升：

在架构设计方面，我学会了如何根据业务需求选择合适的技术方案，如何在各种约束条件下做出权衡。LangGraph 状态图编排和双总线事件驱动架构的设计，让我对复杂系统的架构有了更深入的理解。

在 AI 安全方面，我从理论走向了实践。了解了红队如何生成攻击提示词、蓝队如何构建检测防线、AI Agent 如何被攻击，这些知识是课堂上学不到的。

在前端开发方面，我掌握了 Vue 3 的组合式 API、Pinia 状态管理、WebSocket 实时通信和 ECharts 可视化技术。特别是 WebSocket 的版本比对机制，让我理解了实时数据推送的性能优化思路。

在项目管理和文档编写方面，我学会了如何制定合理的开发计划、如何跟踪项目进度、如何编写完整的技术文档。这些能力的提升对我未来的职业发展非常重要。

## 七、对 AI 安全的认识

这次项目让我对 AI 安全有了更全面和深入的认识。AI Agent 的安全问题不是简单的技术问题，而是一个系统工程。攻击者可能从任何角度突破——输入提示词、工具调用链路、输出内容，甚至是多轮对话的上下文。这意味着防御也必须是一个系统化的工程，而非单点防御。

同时，我也认识到 AI 安全是一个持续对抗的领域。红队在不断进化攻击手段，蓝队也需要不断更新检测策略。我们开发的自动进化功能，正是模拟了这种持续对抗的过程。在实践中，我们看到了攻击变异和防御检测之间的动态博弈，这种博弈在真实的 AI 安全场景中会更加复杂。

## 八、结语

两周的开发时间虽然紧凑，但收获远超预期。从需求分析到架构设计，从编码实现到测试验证，从文档编写到项目交付，我完整地经历了一个软件项目的全生命周期。感谢组员们的信任和配合，感谢老师的指导和建议，让我在技术能力和项目管理能力上都有了显著的成长。

这次项目的经验，无论是技术上的还是管理上的，都将成为我未来学习和工作中的宝贵财富。AI Agent 安全是一个快速发展的领域，我希望未来能在这个方向上继续深入，做出更有价值的工作。
