# 红蓝对抗平台 — 项目总结报告
---
## 1. 项目概述
随着大模型技术飞速发展，AI Agent智能体被大量应用于金融、客服、办公自动化等业务场景。AI Agent具备调用工具、访问业务数据、执行业务操作的能力，极大提升业务效率，但同时带来了提示词注入、角色冒充、越权调用工具、敏感数据泄露等一系列安全风险。传统的AI安全测评大多采用静态数据集单轮测试，无法模拟真实攻击者不断修改攻击提示进行绕过的对抗过程，缺少完整闭环对抗能力，也缺少可视化、可量化的评估手段。

红蓝对抗平台就是面向AI Agent安全评估而设计的自动化对抗演练工具。平台通过红队模拟攻击、蓝队部署防御、目标智能体执行和评估报告生成四位一体的闭环流程，为 AI Agent 安全评估提供自动化、可量化的对抗演练工具。平台模拟真实攻防场景：红队发起攻击，蓝队多层防线拦截；当攻击被防御拦截之后，红队自动对攻击载荷进行变异改写，再次发起攻击，形成“攻击‑检测‑变异‑再攻击”持续对抗闭环，最终输出量化评估报告，帮助测评人员直观发现智能体安全短板。

本项目属于软件实训综合项目，**项目开发周期为 2 周，团队一共3人**，采用前后端分离架构。后端技术栈以Python为核心，使用FastAPI提供REST接口与WebSocket实时服务，基于LangGraph实现攻防流程编排；前端采用Vue 3 + TypeScript，搭配Pinia状态管理与ECharts图表库完成可视化界面。数据库选用SQLite实现本地数据持久化，大模型推理依托Ollama实现本地部署，评估能力可对接DeepSeek外部API。

在团队分工上，组长主要负责整体架构设计、需求梳理、前端页面开发、模型部署与整体流程联调；组员一负责红队全部核心模块，包括攻击生成、数据集解析、5种Payload变异策略开发；组员二负责蓝队防御模块，完成输入检测、工具审计、输出检测三道防线以及YAML检测策略配置。三人协同完成从需求、设计、编码、测试到全套文档输出完整软件工程流程。

> 项目定位说明：本平台为原型实训系统，面向AI安全教学与实验测评，仅支持单机本地部署，不支持多用户隔离、分布式集群等企业级能力，为后续产品迭代打下原型基础。

**各模块补充说明：**
1. **任务管理模块**：完整覆盖任务全生命周期，从创建（PENDING）、运行（RUNNING）、完成（COMPLETED）、失败（FAILED）状态流转。提供数据集查询接口，支持参数校验、异常捕获，任务执行过程中持久化全部任务信息，异常时保存错误堆栈信息便于排查。本期原型暂不支持任务暂停、终止功能。
2. **红队攻击模块**：支持解析Parquet格式RedBench数据集，读取20余个子数据集攻击样本；当样本不足时调用本地大模型补充生成攻击用例；实现语义重写、角色上下文转换、低风险工具序列、多轮迂回、目标分解共5种变异策略；变异任务采用线程池异步执行，不会阻塞主攻防流程。攻击用例记录父子关系，完整保存变异链信息。
3. **蓝队防御模块**：构建输入检测、工具审计、输出检测三道防线，每道防线均实现规则引擎+LLM双通道并发检测。支持`allow`放行、`block`阻断、`degrade`降级三种动作；工具审计环节支持敏感参数脱敏；检测规则全部由YAML配置文件维护，修改防御策略不需要改动业务源代码。
4. **目标模拟模块**：内置金融智能体`financial_agent`与客服智能体`customer_agent`两套业务场景，一共9个模拟工具。所有工具运行在Python逻辑沙箱之内，全部为模拟业务逻辑，不会产生真实业务操作。支持通过YAML配置扩展新的智能体配置。
5. **评估报告模块**：自动计算攻击成功率、检测率、阻断率、误报率、漏报率、风险覆盖率等核心指标，和RedBench基准数据做横向对比；可调用DeepSeek API生成AI分析报告，API不可用时自动切换为规则引擎生成兜底修复建议。
6. **实时可视化模块**：前端实现6个核心组件，包含任务侧边栏、任务状态头部、对抗态势流程图、数据对比面板、安全洞察图表、审计事件时间线。WebSocket实现版本比对推送，前端实现断线自动重连，状态变更实时反馈在页面上。
7. **双事件总线模块**：区分Fast Path同步事件总线和Slow Path异步事件总线。13种同步事件驱动攻防主流程流转；8种异步事件专门处理审计日志、模型追踪、websocket消息等可观测信息；业务模块通过发布‑订阅模式和总线交互，模块之间解耦。

### 2.2 技术成果
项目在实现业务功能之外，沉淀多项针对性解决AI Agent攻防场景的关键技术方案，解决LLM输出不稳定、流程编排复杂、性能开销大、前端实时同步困难等现实工程难题。

| 技术点 | 说明 |
|--------|------|
| LangGraph 状态图编排 | 三节点 DAG 编排，状态传递和条件路由 |
| 双总线事件驱动架构 | Fast Path 同步 + Slow Path 异步，执行路径与可观测路径分离 |
| 双通道并发检测 | 规则引擎 + LLM 模型并行执行，结果合并 |
| 多层容错解析 | JSON → 字典字段 → Markdown 剥离，应对 LLM 输出不稳定 |
| WebSocket 版本比对 | 仅在数据变化时推送，平衡实时性和传输效率 |
| 异步变异进化 | 线程池异步执行，不阻塞主攻防流程 |

**技术点详细说明：**
1. **LangGraph状态图编排**：将复杂的红蓝对抗流程抽象为有向无环图DAG，拆分为攻击链规划、防御分发、评估流三大节点。任务状态使用统一的状态对象在节点之间传递，支持条件分支判断，比如检测结果为block时直接跳转回合结束，不再执行后续工具调用，大幅简化复杂分支逻辑的代码编写，方便调试流程。
2. **双总线事件驱动架构**：把业务执行逻辑和日志观测逻辑完全分开。同步事件总线保证攻防流程的顺序与一致性；异步事件总线处理审计、追踪等非阻塞逻辑，即使日志处理出现异常，也不会打断攻防主流程，提升系统鲁棒性。新增日志导出、指标统计等功能，只需要订阅对应事件，不需要修改原有业务代码。
3. **双通道并发检测**：蓝队的规则引擎和LLM语义检测通过协程并发运行。规则引擎执行速度快，如果提前命中高风险阻断条件，就直接取消还在运行的LLM调用任务，节约大模型推理时间，降低整体耗时。两个通道结果按照“阻断优先、降级次之、放行最后”的规则合并输出。
4. **多层容错解析机制**：专门解决大模型输出格式不可控的工程痛点。LLM返回结果不一定是标准JSON，可能带markdown代码块、多余文本、格式错乱。系统按优先级依次尝试JSON解析、字典字段提取、剥离Markdown标记提取文本，多层兜底，保证尽可能拿到有效Payload，避免因为格式问题造成任务失败。
5. **WebSocket版本比对推送机制**：如果高频无条件全量推送全部任务数据，会造成网络压力大、前端渲染卡顿。系统综合任务状态、当前轮次、攻击用例数量、变异任务数量、审计事件数量等9个维度生成版本快照哈希；每0.5秒对比版本，**只有版本发生变化才推送数据**，兼顾实时性与传输效率。
6. **异步变异进化**：Payload变异需要调用LLM，推理耗时较长。使用线程池异步执行变异任务，主线程可以继续处理其他攻击用例，不用等待变异完成。线程池限制最大工作线程数为1，避免大量并发请求压垮Ollama本地大模型服务。

## 3. 项目亮点
本项目亮点分为架构设计亮点、技术实现亮点、工程实践亮点三个层面，既体现AI安全领域业务针对性设计，也体现规范化的软件工程思想。

### 3.1 架构设计亮点
**双总线事件驱动架构**是最核心的设计亮点。将执行路径（Fast Path）和可观测路径（Slow Path）完全分离，确保：
- 攻击、检测、评估等执行流程在同步总线上完成，保证数据一致性
- 审计、日志、追踪等可观测事件在异步总线上完成，不阻塞主流程
- Slow Path异常不影响主流程，系统稳定性高
- 新增可观测功能只需订阅事件总线，无需修改核心代码

在没有双总线的传统实现中，日志、审计逻辑会直接嵌入业务流程代码中，一方面会增加主流程耗时，另一方面新增观测功能就要改动业务代码，耦合严重。本项目通过事件总线做解耦，业务模块只关心发布事件，不需要关心谁去消费事件，实现关注点分离。

**LangGraph 状态图编排**实现了简洁的流程控制。三节点模型（攻击链规划 → 防御分发 → 评估流）通过有向无环图清晰表达红蓝对抗的执行流程，状态在节点间传递，支持条件路由和回溯。

红蓝对抗存在大量分支判断：输入检测阻断就跳过工具调用；工具审计降级就要替换参数继续执行；满足条件才触发Payload变异。如果全部使用if‑else嵌套编写，代码会十分臃肿，维护难度高。LangGraph把整个攻防流程变成可视化的状态流转，每一个节点职责单一，条件跳转配置清晰，便于后期调试流程问题，也方便后续扩展更多对抗阶段。

### 3.2 技术实现亮点
**多层容错解析**有效应对了 LLM 输出不稳定的问题。当 LLM 变异生成的 Payload 格式不符合预期时，系统依次尝试 JSON 解析、字典字段提取、Markdown 剥离三种方式，最终总能提取到有效内容。

大模型输出不可控是几乎所有LLM应用都会遇到的现实痛点，不能假设模型每次都返回标准JSON。如果只做单层JSON解析，一旦模型输出格式错乱，就直接抛出异常，造成整个变异失败甚至任务中断。多层容错解析从工程层面做兜底，极大提升系统在真实运行环境下的健壮性。

**版本比对机制**优化了 WebSocket 推送效率。通过计算快照版本号（基于 9 个维度），仅在数据变化时推送，避免了无效数据传输。

在最初的原型设想中，方案是固定时间间隔无条件推送全部任务数据，但是在实际测试中发现，当审计事件很多的时候，每次推送数据包体积很大，前端页面频繁重渲染，造成页面卡顿。版本比对方案解决实时性和性能之间的矛盾，在不降低交互体验的前提下，减少网络传输开销。

### 3.3 工程实践亮点
**模块化分层架构**保证了代码的可维护性。后端整体拆分为9个独立模块：API接入层、编排层、红队模块、蓝队模块、目标系统模块、评估模块、事件总线模块、持久化模块、LLM调用模块。各模块职责清晰，基础设施层可复用，业务模块独立，新增模块只需订阅事件总线。模块之间依靠统一接口契约交互，降低模块耦合。小组三个人可以并行开发不同模块，不会出现大量代码冲突。

**配置与代码分离**提升了扩展性。检测策略（blue_policies.yaml）和目标智能体（target_agents.yaml）通过 YAML 配置文件管理，修改配置无需修改代码。

例如，用户想要新增一条关键词检测规则，只需要修改YAML策略文件，不用改动蓝队检测的源代码；想要新增一个模拟智能体，编写对应的YAML描述配置即可。将规则、配置和业务代码解耦，符合软件设计的开闭原则，方便后期调试、调参。

同时，项目严格遵循接口契约先行的思想，开发前就定义好REST接口、WebSocket消息格式、内部模块数据结构（AttackTaskState、RoundResult等），前后端、红队蓝队都按照统一数据结构开发，减少后期联调的冲突。

## 4. 遇到的问题与解决
在两周紧凑的开发周期内，团队遇到多个技术难题，一部分来源于大模型本身的不确定性，一部分来源于前后端联调、性能优化。团队通过查阅文档、小组讨论、参考技术资料、请教指导老师，逐个完成问题攻关。

### 4.1 红队自动进化失败
**问题描述**：LLM变异生成的Payload格式不稳定，有时返回JSON，有时返回纯文本，有时带Markdown代码块标记，存在大量多余解释文本，直接解析JSON会抛出异常，导致变异解析失败，红队自动进化功能失效。

**分析过程**：大模型并不能保证每次严格遵循输出格式指令，即使Prompt明确要求输出JSON，依然会出现格式错乱。初期版本只做单层JSON解析，一旦格式异常，本次变异直接报错，无法生成新攻击用例。

**解决**：实现了多层容错解析。依次尝试 JSON 解析、从字典中提取常见字段、剥离 Markdown 代码块标记取纯文本。三层容错覆盖了所有已知的 LLM 输出格式。如果全部解析方式都失败，则记录审计事件，放弃本次变异，不会终止整个对抗任务，保证任务可以继续运行。

### 4.2 模型拒绝生成恶意攻击提示词
**问题描述**：开源模型（dolphin‑mistral）内置安全对齐限制，当要求生成攻击类内容时，模型会拒绝响应，输出拒绝提示，无法得到有效的攻击Payload，造成红队攻击用例不足。

**分析过程**：大模型默认的安全对齐会拒绝生成用于攻击的提示词，但是本场景是安全测评，不是真实攻击。如果直接强行要求生成攻击内容，很容易触发模型安全防护。

**解决**：将系统提示词重定位为安全评估用途，明确告知模型这是在安全测试场景下生成测试用例，而非实际攻击。同时优先使用 RedBench 数据集加载样本，仅在样本不足时调用 LLM 补充。以数据集样本作为兜底，避免因为模型拒绝输出而导致完全没有攻击用例。

### 4.3 任务进度实时化展示
**问题描述**：WebSocket推送策略不好权衡，如果推送频率过高，大量重复数据不断传输，造成前端页面卡顿、浏览器占用高；推送频率过低，前端状态更新滞后，失去实时可视化的意义。同时，任务运行过程中审计事件会持续新增，全量推送会让数据包越来越大。

**分析过程**：直接固定间隔无条件推送全部任务数据，会传输大量没有发生变化的重复数据，造成资源浪费。

**解决**：实现了版本比对机制。每 0.5 秒检查一次快照版本号（基于任务状态、轮次、用例数量等 9 个维度），仅在版本号变化时推送数据。任务完成后强制推送最后一次全量状态。既保证状态变化之后前端可以快速感知，又避免大量无效传输。

### 4.4 蓝队检测性能
**问题描述**：初期版本规则引擎检测和LLM语义检测串行执行，先执行规则，再调用大模型，单次检测耗时等于两者时间相加，蓝队检测耗时长，整个红蓝对抗流程运行速度很慢。

**分析过程**：规则引擎关键词匹配速度是毫秒级，LLM调用推理需要数秒甚至十几秒。串行模式会叠加两者耗时。同时，当规则引擎已经判定高风险阻断，后续LLM检测就已经没有意义，不需要继续执行。

**解决**：改为双通道并发检测。使用`asyncio.gather`并发执行两个检测任务。规则引擎通常先完成，若命中高风险且判定为阻断，就主动取消还在执行的LLM检测任务以节省开销。两个通道都完成之后，按照严格优先的规则合并检测结果。该优化大幅缩短单次检测耗时。

### 4.5 模块之间数据格式不统一（新增扩写问题）
**问题描述**：开发初期，红队模块输出攻击用例的数据结构、蓝队输出检测结果字段命名不统一，前后端对接时字段名不一致，联调阶段出现大量字段映射错误，接口返回数据前端无法正常渲染。

**分析过程**：小组并行开发不同模块，没有严格遵守预先定义好的数据契约，部分字段命名、字段类型各模块自行修改，造成模块之间对接报错。

**解决**：统一定义核心数据结构体`AttackTaskState`、`RoundResult`，所有模块都复用这套数据模型；编写接口设计说明书，明确每个字段含义、数据类型；每次修改结构体，小组同步更新文档，避免各自私自改动数据结构。

### 4.6 Ollama模型资源竞争（新增扩写问题）
**问题描述**：红队、蓝队、目标智能体需要同时调用不同本地模型，Ollama服务CPU、内存占用很高；当变异异步任务和主攻防流程同时发起大模型请求，请求排队严重，任务执行速度大幅变慢，甚至出现请求超时。

**分析过程**：本地机器硬件资源有限，无法支持无限并发的大模型推理请求。没有做并发限制时，会一次性向Ollama提交大量请求。

**解决**：变异任务线程池限制最大工作线程为1，控制同时执行的LLM变异任务数量；同时在任务约束中注明，本期原型不支持同时运行多个RUNNING状态任务，避免多任务抢占模型资源；设置LLM调用120秒超时时间，超时不会卡死整个任务，记录错误信息之后继续执行后续流程。

## 5. 经验与教训
通过为期两周完整的软件实训项目，团队不仅掌握相关开发技术，也积累团队协作、项目管理、面对AI应用不确定性的工程经验。既有值得继承的成功经验，也发现项目过程中暴露出的不足与教训。

### 5.1 成功经验
1. **架构先行，设计优先于编码**：在开发前花了足够时间进行架构设计，确定了双总线架构和LangGraph编排方案，为后续开发提供了清晰的指引。没有拿到需求就直接写代码，前期花时间梳理模块划分、数据流向、事件定义，虽然占用1‑2天开发时间，但是后期开发少走很多弯路。
2. **模块化开发，并行推进业务模块**：9个模块独立开发，互不阻塞。在基础设施层完成后，业务层可以并行推进。组长负责基础设施、架构、前端；组员专注红队、蓝队业务模块，充分发挥多人团队的优势。
3. **接口契约先定，文档同步更新**：前后端接口契约、内部模块数据结构在开发前就已确定，所有成员共同参考接口设计说明书，修改接口必须同步更新文档，减少了联调阶段的问题。
4. **积极沟通，主动寻求指导**：在开发过程中积极与老师交流，获得了关键词检测到语义检测的转变思路以及RedBench基准的引入建议。遇到技术卡点小组内部先开展讨论，无法解决再查阅官方文档、咨询指导老师，避免卡在同一个问题上浪费大量时间。
5. **重视原型测试与单元验证**：每个小模块完成之后，先做单元验证，比如单独测试红队变异模块、单独测试蓝队双通道检测，确认模块单独运行正常之后，再接入整体流程，不要等到全部写完再做整体联调。

### 5.2 教训
1. **LLM输出不可靠，不能信任大模型结构化输出**：过度依赖 LLM 的结构化输出是不可靠的，必须设计充足的容错机制。不能假设模型一定会严格按照Prompt要求返回JSON，凡是涉及LLM输出解析的地方，都要做好异常捕获、格式容错、降级兜底。
2. **测试时间预留不足**：项目排期中开发占比高，联调测试阶段时间紧张，部分边界情况测试不够充分。很多边界异常场景，例如数据集损坏、模型超时、解析失败，在后期联调才发现。后续项目规划需要预留更多专门的测试时间，提前编写测试用例。
3. **前端复杂度估计不足**：WebSocket实时推送和ECharts图表渲染、态势流程图的调试比预期耗时更长。一开始低估实时交互页面的调试工作量，前端排期时间紧张。对于实时数据流、复杂图表类页面，需要预留充足调试时间。
4. **任务边界约束前期没有明确写进文档**：项目前期没有在文档中明确原型版本不支持同时运行多个任务、不支持任务暂停终止等限制，直到测试阶段暴露资源竞争问题才补充约束。后续项目在需求阶段就应该写清楚版本限制，明确哪些功能本期不做。
5. **文档同步更新不及时**：开发过程中部分接口、字段发生改动，但是文档没有立刻同步更新，出现代码实现和文档描述不一致的情况。需要养成改动代码同步更新文档的习惯。

## 6. 未来展望
本项目完成的是实训原型系统，仍然有较多可以迭代优化的方向，从检测能力、沙箱环境、智能体种类、算法能力、部署形态等方面可以继续扩展：

1. **引入语义向量检测**：在现有规则+LLM双通道基础上，引入向量数据库语义相似度检测，对攻击提示词做向量化比对，提升检测覆盖率和准确率，降低大模型调用次数，减少推理耗时。
2. **支持多模态攻击场景**：目前平台只支持文本攻击Payload，未来可以扩展支持图片、音频等多模态攻击输入，模拟多模态AI Agent的安全测评场景。
3. **升级隔离沙箱环境**：当前为Python逻辑沙箱，未来引入Docker容器沙箱或者WASM沙箱，提供更真实、更强隔离性的工具执行环境，模拟更贴近真实业务系统的运行条件。
4. **扩展更多类型目标智能体**：当前只有金融、客服两种模拟智能体，后续可以新增医疗问诊、办公自动化、代码执行智能体等场景，拓宽平台测评适用范围。
5. **引入强化学习实现自适应攻击策略**：当前红队变异依靠预设的5种固定策略；后续可以引入强化学习，让红队根据历史对抗结果自动学习最优变异方式，实现自适应攻击，进一步模拟真实攻击者行为。
6. **SaaS化部署与多用户能力**：原型仅支持单机本地运行，未来可以实现SaaS网页部署，增加用户登录、权限管理、任务隔离，降低普通用户使用门槛，不用本地部署Ollama即可使用测评能力。
7. **策略可视化配置界面**：当前修改蓝队防御策略需要手动编辑YAML文件；后续开发网页端策略编辑器，支持可视化新增、修改检测规则，不需要接触配置文件。
8. **报告导出能力**：支持评估报告一键导出PDF、Word文档，方便测评人员直接输出交付测评材料。

## 7. 总结
红蓝对抗平台项目在短短 2 周内从零到一完成了从需求分析、架构设计、编码开发、测试验证到全套文档编写的完整软件工程实践。团队一共3人，分工明确、沟通协作高效，克服开发周期短、LLM输出不稳定、实时可视化调试复杂等多项难点。最终交付的平台功能完整，架构设计合理，实现“攻击‑检测‑进化‑再攻击”完整闭环红蓝对抗流程，满足AI Agent安全自动化测评的原型需求。

在技术层面，团队成员实践了FastAPI后端开发、LangGraph流程编排、事件驱动架构、WebSocket实时通信、Vue3前端开发、Ollama本地大模型集成等多项前沿技术，对AI Agent安全领域的攻击手段、防御方案、量化评估方法建立直观理解。

在工程实践层面，完整经历软件项目全生命周期，体会架构先行、模块化开发、接口契约、文档同步的重要性，同时也认识到大模型应用开发与传统软件的差异：大模型存在输出不确定性，必须在工程层面做大量容错、降级、兜底处理。

本次实训也暴露出团队的一些不足，因为没有接触过网络安全模块，初期对于项目的总展望是相当错误的，幸好有老师的交谈给出了一个大概的框架，除此之外还有一些规划上的问题，比如测试时间预留不足、部分边界场景考虑不够周全，这些经验教训可以为今后其他项目提供参考。整体而言，本次实训项目不仅锻炼编码能力，也锻炼团队协作、问题排查、文档撰写综合能力，积累宝贵的项目实战经验。
