# 红蓝对抗平台 — 个人工作分工及完成情况

---

## 一、项目概述

本项目为“红蓝对抗平台”，是一个面向 AI Agent 安全评估的自动化对抗演练系统。平台以 FastAPI + LangGraph 为后端核心，Vue 3 + TypeScript 为前端框架，构建了红队攻击模拟、蓝队防御检测、目标系统执行、评估报告生成四位一体的完整对抗流程。系统支持基于 RedBench 数据集的自动攻击用例生成、EvoSafety 策略的对抗性 Payload 自动进化、规则引擎与 LLM 双通道并发检测，以及通过 WebSocket 实时推送任务进度。

## 三、个人工作详述

### 3.1 需求分析与方案设计

在项目启动阶段，组织小组进行多轮需求讨论，将模糊的“红蓝对抗”概念逐步细化为可落地的技术方案。具体工作包括：

- 与组员讨论后，将需求总结为“红队攻击生成 → 蓝队防御检测 → 目标系统执行 → 评估报告生成”的四阶段流程。
- 与指导老师进行技术交流，在老师的建议下确定引入 RedBench 数据集作为攻击种子样本，并采用“规则引擎 + LLM 模型”双通道并发检测方案替代纯关键词匹配，从架构层面提升检测的准确性和鲁棒性。
- 将讨论结果转化为技术文档和接口契约，指导组员按模块分工开发。

### 3.2 整体架构设计

**（1）模块分层设计**

将系统划分为 9 个独立模块，定义清晰的模块边界和接口：编排层负责 LangGraph 状态图，控制攻击、防御、评估的主流程；红队模块负责攻击链规划、变异进化、RedBench 数据集适配；蓝队模块负责输入检测、工具审计、输出检测三道防线；目标系统模块负责目标智能体管理和沙箱工具执行；评估模块负责指标计算、评分和报告生成；事件总线模块负责 Fast Path 和 Slow Path 双总线；持久化模块负责数据库模型和 CRUD 操作；模型调用模块负责统一的 LLM 客户端；可观测性模块负责链路追踪、审计日志和结构化日志。

**（2）双总线事件驱动架构**

设计并实现了 Fast Path Bus（同步阻塞，管理红蓝攻防执行路径）和 Slow Path Bus（异步非阻塞，承载审计日志、模型追踪、指标上报等可观测事件）。

Fast Path Bus 采用同步执行和发布-订阅模式，定义了 13 种事件类型，包括攻击请求、输入接收、工具允许、工具阻断、输出阻断、回合结果等，覆盖攻防执行全路径。Slow Path Bus 采用异步执行，使用 Python 协程将处理器放入后台任务，不阻塞主流程，定义了 8 种事件类型，包括防御反馈、审计日志、模型追踪、工具追踪、报告事件等。两个总线通过 EventContext（包含任务 ID 和追踪 ID）关联，确保所有事件可追溯到具体任务和调用链。默认处理器 InMemoryTelemetrySink 按事件类型分桶存储，在启动时自动注册所有事件类型的处理器。

**（3）LangGraph 状态图编排**

采用 LangGraph 的 StateGraph 构建任务执行流程，定义了三个节点：攻击链规划节点负责生成攻击用例，防御分发节点负责执行攻击并协调红蓝对抗，评估流节点负责生成评估报告。三个节点按顺序执行，输入输出均为统一的 AttackTaskState 状态对象，确保状态一致性。通过闭包注入的方式将数据库回调和持久化逻辑注入到防御分发节点中，实现节点与持久化层的解耦。主运行函数封装了完整的任务生命周期：状态初始化、图执行、异常处理、持久化、状态更新。

**（4）数据流设计**

梳理了完整的系统数据流：用户创建任务后，系统初始化任务状态；红队从 RedBench 数据集或 LLM 生成攻击链；然后逐个执行攻击用例，每个用例经历六个阶段——攻击请求、蓝队输入检测、目标智能体 LLM 决策和工具调用、蓝队工具审计、沙箱执行工具、蓝队输出检测，最终得到回合结果判定（允许、阻断或降级）。红队根据回合结果判断是否需要进化，若需要则异步生成变异后的新用例追加到待执行队列尾部。所有攻击用例执行完毕后，系统生成评估报告，包括指标计算、评分和 RedBench 基准对比。整个过程中，WebSocket 每 0.5 秒向前端推送任务状态快照，同时将所有数据持久化到数据库的 AttackCase、DetectionResult、AuditEvent、EvaluationReport 四张表中。

### 3.3 核心流程开发

**（1）攻击链规划节点**

攻击链规划节点负责从 RedBench 数据集或 LLM 生成攻击用例列表。在实现中，优先使用 RedBench 数据集中的真实攻击样本作为种子，当数据集样本不足时才调用 LLM 补充生成。通过 RedBench 数据集适配器加载 Parquet 格式的数据，根据风险类型进行映射和筛选，确保攻击用例的多样性和真实性。

**（2）防御分发节点**

防御分发节点是整个系统最核心的编排函数。它维护一个待执行队列和一个变异任务字典，循环处理攻击用例：优先执行待执行队列中的用例，当队列为空时等待变异任务完成。每个攻击用例执行完毕后，调用红队指挥官的进化判定方法判断是否需要进化。若需要进化，通过线程池（最大工作线程数为 1）异步提交变异任务，不阻塞主循环。变异完成后的新用例追加到待执行队列队尾，实现“执行、进化、再执行”的闭环。每个回合完成后通过回调函数触发数据库持久化。

**（3）攻击执行函数**

单次攻击的执行流程分为六个阶段。第一阶段是攻击请求，发布攻击请求事件并记录审计日志。第二阶段是输入检测，蓝队指挥官对攻击提示词进行检测，若被阻断则直接返回结果。第三阶段是目标执行，目标管理器调用目标智能体的 LLM 决策是否执行工具调用。第四阶段是工具审计，若无工具调用则直接进入输出检测；若有工具调用，蓝队指挥官进行审计；若被阻断则返回结果；若被降级，则使用降级后的工具参数继续执行。第五阶段是沙箱执行，目标管理器在沙箱中执行工具或降级后的工具。第六阶段是输出检测，蓝队指挥官对目标输出进行检测，返回最终回合结果。每个阶段都通过 Fast Path 发布事件、通过 Slow Path 记录审计，确保全链路可追溯。

**（4）评估流节点**

评估流节点调用评估报告生成函数，计算攻击成功率、检测率、阻断率、降级率、误报率、漏报率、风险覆盖率等核心指标，并与 RedBench 基线数据进行对比分析。同时，通过 DeepSeek API 从红方视角、目标系统视角、蓝方模型视角三个维度生成修复建议。评估完成后，将评估指标和链路追踪数据作为审计事件追加到 Slow Path。

**（5）蓝队指挥官**

蓝队指挥官类整合了蓝队三道防线。输入检测方法调用输入检测器对攻击提示词进行检测，采用规则引擎和 LLM 模型双通道并发模式。工具审计方法调用工具审计器，进行角色权限校验、敏感字段降级和 LLM 辅助判定。输出检测方法调用输出检测器对目标执行结果进行检测。

**（6）红队指挥官**

红队指挥官类负责攻击链规划和变异进化。攻击链规划方法从 RedBench 数据集加载提示词，不足时调用 LLM 生成。进化判定方法根据回合结果（是否成功、失败阶段、是否降级）和剩余轮次决定是否需要进化。变异任务构建方法根据失败阶段自动选择最优的变异策略。变异执行方法通过 LLM 对原始 Payload 进行语义重写，生成新的攻击用例。

**（7）目标系统管理器**

目标系统管理器类管理两种目标智能体——金融智能体和客服智能体。目标规划方法调用目标智能体的 LLM 进行决策，判断是否需要调用工具。工具执行方法在沙箱中安全执行工具调用，支持 Python 沙箱和 WASM 沙箱两种执行环境。

**（8）LLM 统一客户端**

LLM 统一客户端实现了统一的 LLM 调用接口。本地 Ollama 调用用于红队、蓝队、目标模型的推理，外部 DeepSeek API 调用用于评估模型的推理。提供四个角色方法——红队对话、蓝队对话、目标对话、评估对话，各自使用对应的默认模型。启动前进行 Ollama 服务健康检查，确保模型可用。

**（9）数据库模型设计**

设计了 5 张核心数据库表。Task 表是任务主表，包含状态、目标智能体、风险类型、攻击技能、轮次、模型配置等字段。AttackCase 表是攻击用例表，记录每次攻击的提示词、风险类型、变异策略、父子关系等。DetectionResult 表是检测结果表，记录每次检测的阶段、动作、风险等级、置信度等。AuditEvent 表是审计事件表，记录 Fast Path 和 Slow Path 的所有事件。EvaluationReport 表是评估报告表，记录攻击成功率、检测率、阻断率、RedBench 对比等指标。

**（10）API 与 WebSocket 端点**

REST API 提供了 7 个端点：创建任务、启动任务、任务列表、任务详情、评估报告、审计事件、RedBench 数据集列表。WebSocket 端点提供了任务状态实时推送，每 0.5 秒将当前任务状态打包为快照推送给前端，快照包含任务基本信息、攻击用例列表、突变任务列表、检测结果、审计事件、评估报告。

**（11）可观测性模块**

设计了完整的可观测性体系。链路追踪模块实现了 TraceRecorder 和 TraceSpan，支持嵌套调用链追踪和耗时计时。审计日志模块实现了 AuditTrail 追加式审计记录，支持导出。结构化日志模块实现了 JSON 格式的日志输出，便于日志分析和检索。

**（12）红队自动进化机制**

在编排层实现了完整的红队自动进化机制。当蓝队检测到攻击失败时，系统根据失败阶段自动推荐最优变异策略——输入阶段失败推荐语义重写和角色上下文转换策略，工具阶段失败推荐低风险工具序列和多轮迂回策略，输出阶段失败推荐目标分解和多轮迂回策略。变异任务通过线程池异步提交，不阻塞主执行流程。变异完成后，新用例自动追加到待执行队列尾部，实现“检测、进化、再攻击”的持续对抗闭环。

**（13）双通道并发检测机制**

在蓝队检测模块中实现了规则引擎和 LLM 模型双通道并发检测。使用 Python 协程同时启动规则检测和模型检测两个任务，规则检测通常先完成。若规则检测命中高风险，立即取消模型检测任务，避免无效的 LLM 调用开销。合并两个检测结果时，优先采用更严格的判定——阻断优先于降级、降级优先于允许。模型检测被取消时通过 Slow Path 记录取消事件，保留可观测性。

### 3.4 关键技术难点攻关

**（1）红队自动进化失败问题**

在实现红队 Payload 自动进化时，LLM 模型返回的输出格式极不稳定——有时返回 Markdown 包裹的 JSON，有时返回纯文本解释，有时 JSON 多了一层嵌套。原始的解析器仅接受纯净的 JSON 对象，导致变异链路频繁崩溃。

**解决方案**：设计了多层容错解析函数。第一层尝试标准 JSON 解析；第二层从解析后的字典中提取常见字段名（如 rewritten_payload、mutated_prompt、payload、prompt、text 等），只要找到任意一个非空字符串就返回；第三层若解析结果本身就是字符串，直接返回；第四层剥离 Markdown 代码块标记（三个反引号），提取其中的纯文本内容。同时，在变异重写提示词中加入了严格的输出约束，明确禁止模型返回 JSON、Markdown、代码块、标签、解释等非纯文本格式。经过这些优化，变异成功率从约 60% 提升到了 95% 以上。

**（2）模型无法生成恶意攻击提示词问题**

红队使用的本地 Ollama 开源模型在收到“生成恶意攻击提示词”的指令时，会触发合规安全机制，返回“我不能帮助您进行恶意活动”等拒绝回复。

**解决方案**：采用了三层策略。第一层是系统提示词重定位——将红队系统提示词从“攻击者”定位改为“AI Agent 安全评估平台中的红队测试者”，并强调“仅用于安全评估目的”，从而规避模型的合规拒绝机制。第二层是 RedBench 数据集兜底——优先从 RedBench 数据集中加载真实的攻击提示词作为种子样本，仅当数据集样本不足时才调用 LLM 补充生成，这样即使 LLM 拒绝生成，系统仍能获取足够数量的攻击用例。第三层是生成数量校验——对 LLM 返回的 JSON 数组进行数量校验，不满足要求时抛出明确异常，便于上层调用方感知和处理。

**（3）任务进度实时化展示问题**

后端执行一个完整任务可能需要数分钟，前端需要实时展示执行进度。传统的轮询方案存在频率难以权衡的问题——太快会压垮服务器，太慢则不够实时。

**解决方案**：设计了 WebSocket 推送架构。后端每 0.5 秒将当前任务状态打包为快照推送给前端，快照包含任务基本信息、攻击用例列表、突变任务列表、检测结果、审计事件、评估报告。同时实现了版本比对优化——基于任务状态、当前轮次、更新时间、攻击用例数量等生成快照版本号，仅在版本变化时才推送，避免重复数据。前端状态管理中的快照应用方法接收快照后立即更新所有响应式状态，UI 自动刷新。同时实现了断线自动重连（1.5 秒间隔）和任务完成自动关闭连接。
