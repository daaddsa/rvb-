## 柯涵 （红队 & 编排引擎，架构思考型，侧重算法与流程逻辑）

### **开发感想**

本次负责红队攻击生成、任务编排引擎以及大模型调用层的开发。在最开始设计任务图调度框架时，我原本以为只要写好状态流转逻辑就可以跑通完整攻击链路，但真正落地才意识到，大模型输出的不可确定性是整个模块最大的变数。很多时候流程代码没有报错，但 LLM 返回格式错乱、输出内容脱离预设场景，直接导致整个攻击任务中断。

团队协作过程中印象最深的是模块间接口对齐。前期只关注自己模块内部逻辑，没有提前和 B、C 约定好事件数据结构，在第一次联调的时候出现大量字段不匹配，数据传过去无法解析。通过集体梳理events.py公共数据模型，统一输出规范之后，模块之间的调用才顺畅起来。整个项目让我体会到，做系统不只是实现功能，还要对异常、模型失效、任务中断这些边界情况做兜底处理。

### **实现困难点**

1. LLM 输出不稳定：红队攻击提示词很难做到 100% 输出结构化 JSON，经常出现格式错乱，直接打断任务编排图执行流程。

2. 编排引擎状态复杂：攻击任务存在分支、重试、中断恢复，任务节点多，状态机维护成本高，很容易出现状态死锁。

3. 模块边界耦合：红队需要调用蓝队沙箱执行结果，又要向 C 模块推送事件数据，稍有不注意就会引入跨模块强依赖。

4. 超时与并发问题：多个红队任务并行运行，大模型接口调用超时，会造成任务堆积。

### **迭代想法**

1. 增加 LLM 输出修复层：增加格式校验 + 自动修复模块，当大模型返回非标准 JSON 时，尝试自动解析，解析失败再标记任务失败，而不是直接崩溃。

2. 完善任务持久化：编排任务支持断点续跑，任务异常中断之后，可以从失败节点继续执行，而不是从头重新运行整套攻击流程。

3. 解耦模块调用：将跨模块的直接函数调用改为事件队列消息通知，降低模块之间的耦合。

### **后续开发思路**

优先把编排引擎的异常兜底逻辑补齐，完善任务状态监控；针对红队攻击策略，扩充攻击模板库，做策略权重配置，实现多样化攻击路径；同时优化 LLM 调用池，增加限流、重试，提升并发任务处理能力；后续可以引入简单的决策算法，让红队可以根据蓝队反馈动态调整攻击策略。
