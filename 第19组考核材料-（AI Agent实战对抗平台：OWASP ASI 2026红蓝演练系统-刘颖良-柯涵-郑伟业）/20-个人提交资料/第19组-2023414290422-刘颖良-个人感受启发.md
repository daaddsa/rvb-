# 红蓝对抗平台 — 个人感受与启发

## 一、对 AI 安全领域的认知转变

在这个项目之前，我对网络安全的理解主要停留在传统的漏洞扫描、渗透测试、防火墙策略等方面。当第一次在需求讨论会上接触到“AI Agent 安全评估”、“红蓝对抗”、“提示词注入”这些概念时，我意识到这是一个全新的领域——AI 智能体没有传统意义上的端口和服务，攻击方式完全不同于传统的网络攻击，防御思路也需要重新构建。

传统网络安全主要关注代码层面的漏洞和网络层面的攻击面，而 AI Agent 安全则不同。攻击者不需要寻找系统漏洞，只需要通过精心设计的自然语言指令，诱导 AI 智能体执行不该执行的操作。这种攻击范式的转变让我认识到，安全工作正在从代码层面扩展到语义层面，这是这个项目给我带来的最重要的认知更新。

作为组长，我承担了架构设计的角色。现在回头看，这个项目不仅让我积累了技术经验，更重要的是让我对 AI 安全这个方向有了系统性的理解。

## 二、架构设计的过程与体会

作为架构师，我的核心任务是将一个模糊的需求转化为可落地的系统设计。这个过程的难度比我预想的要大得多。

项目初期，小组讨论时提出了大量问题：红队怎么生成攻击？蓝队在哪里检测？目标系统怎么执行？检测结果怎么反馈给红队做进化？数据怎么存储？前端怎么展示？每个问题单独看都有解决方案，但把这些方案组合成一个协调运行的系统，需要找到一条贯穿始终的主线。

经过反复思考，我确定了这个系统的核心是“事件流”。红队发起攻击、蓝队检测、目标执行、评估报告，本质上都是一系列事件的产生和消费。基于这个认知，我设计了双总线架构——Fast Path 负责同步的执行流程事件，Slow Path 负责异步的审计和可观测事件。每个模块只需要订阅自己关心的事件类型，不需要了解其他模块的内部实现，模块间的耦合度大幅降低。

这个设计过程让我学到的一个重要经验是：在做架构设计时，不要急于确定技术选型和具体实现，而是先想清楚系统的核心是什么，围绕核心来组织模块，架构自然会清晰起来。

## 三、与指导老师交流的收获

项目开发过程中，我们多次与指导老师进行深入交流，这些交流对项目的技术方向产生了重要影响。

有一次，我向老师展示了蓝队检测方案——基于关键词匹配的规则引擎。老师问了一个关键问题：如果攻击者把“转账”写成“转 账”或者用拼音代替，规则还能命中吗？这个问题直接暴露了关键词匹配方案的局限性。在老师的建议下，我们将检测架构升级为“规则引擎加 LLM 模型”双通道并发检测——规则引擎快速拦截明显违规的输入，LLM 模型负责理解语义层面的攻击意图，两者并发执行，规则命中高风险时直接取消模型调用以节省开销。

老师还建议我们引入 RedBench 数据集作为红队攻击的种子样本。这个建议后来被证明非常关键——当红队 LLM 模型因为合规限制而拒绝生成恶意提示词时，RedBench 数据集中的真实攻击样本成为了可靠的兜底方案，确保了红队攻击用例的稳定产出。

这些经历让我认识到，在技术选型和方案设计阶段，多与有经验的人交流讨论，往往能发现自己没有考虑到的盲点，避免在错误的方向上投入过多时间。

## 四、三个关键技术难点的攻克过程

### 4.1 红队自动进化失败

在实现了基础的攻击、检测、评估流程后，我们开始做红队的自动进化功能——当蓝队检测到攻击失败时，红队自动对 Payload 进行变异，然后发起新一轮攻击。

这个功能在理论上没有问题，但实际运行时频繁崩溃。根本原因在于 LLM 模型的输出格式极不稳定：有时返回 Markdown 包裹的 JSON，有时多了一层嵌套，有时干脆返回一段纯文本解释。我们原来的解析器只接受标准的 JSON 对象，遇到这些格式就直接报错，导致变异链路中断。

我花了两天时间专门解决这个问题。尝试了多种方法：在提示词中加更严格的格式约束、用正则表达式提取、尝试不同的 JSON 解析库，但都不够稳定。最终，我设计了一个多层容错解析函数：第一层尝试标准 JSON 解析，第二层从解析后的字典中提取常见字段名，第三层直接返回字符串，第四层剥离 Markdown 代码块标记后取纯文本。这个多层容错的设计让变异成功率从约 60% 提升到了 95% 以上。

这个经历让我认识到，在 AI 工程中，模型输出本质上是不稳定的，不能假设它总是按照预期格式返回。必须为各种可能的失败模式设计兜底方案，这是 AI 工程和传统软件开发的一个重要区别。

### 4.2 模型无法生成恶意攻击提示词

我们使用的是 Ollama 本地部署的开源模型。当要求它生成恶意攻击提示词时，模型的合规安全机制会拒绝执行，返回“我不能帮助您进行恶意活动”之类的回复。

这个问题在小组讨论时一度让我们非常被动——如果连攻击提示词都生成不了，红队模块就失去了存在的意义。

后来我们调整了思路，不再要求模型以“攻击者”的身份生成恶意内容，而是将系统提示词重新定位为“AI Agent 安全评估平台中的红队测试者”，强调所有操作仅用于安全评估目的。这个定位的调整成功规避了模型的合规拒绝机制。同时，我们引入了 RedBench 数据集作为兜底方案——优先从数据集中加载真实的攻击提示词作为种子样本，仅当数据集不足时才调用 LLM 补充生成。这样即使 LLM 拒绝，系统仍能获取足够的攻击用例。

这个问题的解决过程让我认识到，有时候问题的关键不在于技术本身，而在于如何定义问题。换个角度描述问题，可能就能绕过原本看似不可逾越的障碍。

### 4.3 任务进度实时化展示

后端执行一个完整任务可能需要数分钟，前端需要实时展示执行进度。如果等任务完成后再一次性返回结果，用户体验会非常差。

我们首先考虑了轮询方案，但轮询频率难以权衡——频率太高会增加服务器压力，频率太低则不够实时。最终选择了 WebSocket 推送方案：后端每 0.5 秒将当前任务状态打包成快照推送给前端，快照包含任务基本信息、攻击用例列表、突变任务列表、检测结果、审计事件和评估报告。同时实现了版本比对优化，仅在数据变化时才推送。

实际部署后还遇到了网络波动导致 WebSocket 断连的问题，我们在前端状态管理中加入了自动重连机制（1.5 秒间隔重试）和任务完成自动关闭连接，确保整个流程的健壮性。

这个功能的实现让我认识到，一个好的实时交互体验，需要在前端、后端、网络协议三个层面协同设计，单独优化某一层是不够的。

## 五、团队协作方面的收获

作为组长，我在团队协作方面也有不少收获。

项目初期，我们犯了一个常见的问题——大家各自写各自的代码，等到合并时才发现接口对不上、数据格式不一致。后来我要求所有模块间通信的数据结构必须先定义清楚，所有人按接口契约开发，谁违反契约谁负责修正。这个规定让集成效率提升了很多。

另一个经验是分工要明确且不重叠。在分配任务时，我让每个成员负责一个独立的模块，模块之间的边界清晰，大家不需要频繁互相等待。这样即使有人进度稍慢，也不会阻塞其他人的工作。

我也学会了在管理上适当放手。作为组长，我最初想亲自检查每一行代码，但很快发现这不现实。后来改为只关注模块间的接口和核心流程，把具体的实现细节交给组员自己把控。信任团队成员的能力，是提高整体效率的有效方式。

## 六、对未来的思考

项目接近尾声时，我反思了平台目前的能力和不足。我们的检测规则目前主要依赖关键词匹配，LLM 模型的能力也受限于本地部署的硬件条件。如果攻击者使用更高级的对抗性技术，比如将恶意意图编码为 Base64、使用隐写术、或者通过多轮对话逐步引导，系统很可能无法有效检测。

但这也正是 AI 安全领域的特点——安全从来不是一个可以“完成”的状态，而是一个持续对抗、持续进化的过程。红队在进化攻击手段，蓝队也在更新检测能力，这个平台的价值在于它建立了一个可以持续迭代的对抗框架。

从更长远的角度看，随着 AI Agent 越来越多地接入真实的生产环境——处理金融交易、管理客户数据、控制物理设备——AI 安全的重要性只会越来越高。我希望未来能继续在这个方向上深入探索，不仅停留在检测恶意输入的层面，而是研究更底层的安全机制，比如沙箱隔离、权限最小化、行为审计、对抗性训练等。

## 七、结语

在实践课开发前，我对 AI Agent 安全几乎一无所知。四个月后，我和团队从零开始搭建了一个完整的红蓝对抗平台，包含攻击生成、防御检测、自动进化、实时可视化、评估报告等全套功能。

这个过程有焦虑和挫败，也有攻克难题后的满足感，有看到前端界面第一次实时展示攻击流程时的兴奋，也有和老师、组员们深入讨论后理清思路时的畅快。这些经历让我切实体会到，技术能力是在解决实际问题的过程中逐步积累的，而真正推动成长的，是那些一开始觉得难以完成的任务。

感谢指导老师的悉心指点，感谢每一位组员的全力付出。
